Decisiones de seguridad — Portal PerroniPhone

Este documento explica qué controles de seguridad implementa el portal académico de PerroniPhone, por qué se eligieron y cuáles son sus límites. La versión en Markdown está en SECURITY.md en la raíz del repositorio.

Alcance: frontend HTML/CSS/JS + API REST en Laravel 11 (PHP 8.3) + MySQL 8, detrás de Nginx, todo en Docker Compose. Todos los usuarios, correos y contraseñas son ficticios. La v1 del proyecto era 100% del lado del cliente y la v2 usaba ASP.NET Core + SQL Server; su historia queda en Git.

1 Autenticación

1.1 Contraseñas nunca en texto plano

Decisión
Cada fila de usuarios guarda un salt aleatorio y un hash_password derivado con PBKDF2-HMAC-SHA256, 100,000 iteraciones (app/Services/PasswordHasher.php). La comparación usa hash_equals(), en tiempo constante.
Por qué
PBKDF2 es lento a propósito: encarece la fuerza bruta y los diccionarios si alguien obtuviera la base.
Límite
Hoy se prefiere Argon2id o bcrypt (Hash::make() de Laravel). Se conservó PBKDF2 por continuidad con la v2.

1.2 Sin enumeración de usuarios

Decisión
Si el correo no existe, la contraseña es incorrecta o la cuenta está bloqueada, la respuesta es siempre 401 "Correo o contraseña incorrectos.". El motivo real solo se explica cuando la contraseña es correcta. Para correos inexistentes se calcula igualmente un PBKDF2 de relleno, así la respuesta tarda lo mismo.
Por qué
Nadie puede averiguar qué correos están registrados ni por el mensaje, ni por el código HTTP, ni midiendo el tiempo de respuesta.

1.3 Bloqueo por intentos fallidos (por cuenta)

Decisión
Al 5º intento fallido la cuenta se bloquea 2 minutos (bloqueado_hasta). Durante el bloqueo los intentos no cuentan; al vencer, el contador vuelve a cero. El incremento es atómico (transacción con SELECT … FOR UPDATE): peticiones simultáneas no pueden saltarse el límite.

1.4 Límite de peticiones (por IP)

Decisión
POST /api/auth/login acepta 20 peticiones por minuto por IP (AppServiceProvider). Laravel solo confía en X-Forwarded-For si la petición viene de una red privada (nginx o ngrok), así que la IP no se puede falsificar.
Por qué
El bloqueo por cuenta no frena a quien prueba muchas cuentas distintas; éste sí, y además limita el costo de CPU de PBKDF2.

2 Gestión de sesión (JWT)

Decisión
La API emite un JWT firmado (HS256) con vigencia de 20 minutos. El navegador lo guarda en sessionStorage y lo envía en Authorization: Bearer. APP_KEY y JWT_SECRET no están en el repositorio ni en la imagen: docker/entrypoint.sh los genera al crear cada contenedor.
Cuenta bloqueada = sesión terminada
El middleware cuenta.activa revisa el estado en la base en cada petición: si un administrador bloquea una cuenta, su token deja de servir de inmediato.
Límite
No hay lista de revocación (cerrar sesión borra el token del navegador, pero sigue siendo válido hasta expirar) y un XSS podría leer sessionStorage. En producción: cookie httpOnly + Secure + SameSite y refresh tokens.

3 Control de acceso (RBAC por permisos)

Una sola fuente de verdad
laravel-app/database/data/permisos.json define los permisos de cada rol; el seeder lo sincroniza con la tabla permisos en cada arranque.
Backend (la barrera real)
Cada ruta exige un permiso con el middleware permiso:<nombre>, que consulta el rol actual de la base: gestionar_usuarios (directorio y bloqueo), editar_roles (cambio de rol), ver_bitacora y ver_contabilidad. Nadie puede modificar su propia cuenta y solo un administrador puede modificar a otro, así que siempre queda al menos un administrador activo.
Frontend (solo interfaz)
El login devuelve la lista de permisos del usuario; las páginas la usan para bloquear enlaces y redirigir, pero nunca es la barrera.
Límite
Las matrices GRC de gobierno.html viven en assets/js/grc.js, un archivo público: esa restricción es de interfaz (el análisis también es público en docs/).

4 Inyección SQL y XSS

Inyección SQL
Todas las consultas usan Eloquent / Query Builder con parámetros enlazados; nunca se concatena texto del usuario en SQL.
XSS
Todo dato dinámico se inserta en el DOM con escapeHTML(), que convierte & < > " ' en entidades HTML.

5 CSRF y CORS

Decisión
La API no usa cookies de sesión: la credencial viaja en el header Authorization, que un sitio externo no puede hacer que el navegador envíe solo, por lo que no hace falta token anti-CSRF. Frontend y API comparten origen, así que CORS no permite ningún origen externo por defecto.

6 Validación de entradas

Servidor
El login exige un correo con formato válido (máx. 150 caracteres) y una contraseña de máx. 200. Roles y estados se validan contra listas blancas; los IDs de las rutas solo aceptan números.
Cliente
El correo se valida con una expresión regular antes de enviarlo y se muestra la fuerza estimada de la contraseña (solo informativo).

7 Bitácora de seguridad (auditoría)

Decisión
La tabla bitacora registra accesos correctos, intentos con correos inexistentes, bloqueos automáticos, cambios de rol y bloqueos manuales con el código del responsable. Solo la ven los roles con ver_bitacora.
Límite
No se guarda la IP de origen y los registros no son inmutables.

8 Infraestructura (Docker)

Decisión
El .env no se versiona; cada contenedor crea el suyo con llaves nuevas. APP_DEBUG=false: un error 500 no muestra stack traces. MySQL y phpMyAdmin solo escuchan en 127.0.0.1; solo se publica nginx (puerto 8080). Nginx bloquea archivos ocultos como .env.
